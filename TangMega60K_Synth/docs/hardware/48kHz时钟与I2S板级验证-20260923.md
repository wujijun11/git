# 48 kHz 时钟与 I2S 板级验证（2026-09-23）

## 验证对象

独立工程 `clock48/BoardAudio48kGAO.gprj` 使用 `board_audio_48k_gao_top`，复用主工程的 `live64_system_top`、64 声部音源和 24 位标准 I2S 发送器。底板 50 MHz 时钟经两级 PLLA 依次生成标称 38.4 MHz 和 49.152 MHz。原发送器每帧使用 1024 个音频时钟，因此标称采样率为 48 kHz，BCLK 为 3.072 MHz。此入口仅把 I2S 信号接入片内 GAO；外部 DAC 引脚尚未连接。

本工程的位流为 `clock48/impl/pnr/ao_0.fs`，SHA256 为 `24454E10D54FF9A39069215ED7BB471A801949240597DC797A65547B50099031`。原 50 MHz 板级 GAO 位流 `impl/pnr/ao_0.fs` 的 SHA256 仍为 `C8958860C0C4394B5CFD2E7FC11A349229BDBA240642F0F29CE1BF1208C6EA8C`，没有被这个独立工程覆盖。

Gowin V1.9.12 布局布线完成，时序报告识别 38.400 MHz 与 49.152 MHz 两个生成时钟，Setup/Hold 违例端点均为 0。PR1014 仍提示板载 50 MHz 输入 V22 使用通用时钟布线资源；这是板卡输入引脚的限制，不应把 0 时序违例理解为该警告已消失。

## 实物检查

目标器件为 GW5AT-60B（ID `0x0001481B`）。Gowin Programmer 通过 DEBUG USB 将该位流下载到 FPGA SRAM，下载成功后 Read Device Codes 显示 User Code `0x000099EE`、Status Code `0x70026020`。没有写入 Flash；断电或重新配置后需要重新下载。

片内监测以板载 50 MHz 作参考，每 5,000,000 个参考周期测量一次音频时钟。三份有效 GAO 采集都读到 `0x04B0000`，即 4,915,200 个音频时钟周期，符合设计的 49.152/50 频率比。PLL 锁定、时钟测量有效、频率比检查通过，且采集窗口内 `error=0`、`fault=0`、`underruns=0`、`active_count=64`。这个比值检查没有独立测量板载晶振的绝对频率；实际采样率仍随其频差变化。

| GAO 文件 | 完成轮数 | 有效采样点 | BCLK 周期 | 解码结果 |
| --- | ---: | ---: | ---: | --- |
| [第一次](gao-48k-20260923/board_audio_48k_core0.csv) | 175 | 4096 | 16 个音频时钟 | 7 个完整非零 24 位样本 |
| [重新下载后的较晚一次](gao-48k-20260923/board_audio_48k_later_core0.csv) | 467 | 4096 | 16 个音频时钟 | 7 个完整非零 24 位样本 |
| [重新接电并再次下载后](gao-48k-20260923/board_audio_48k_reconnected_core0.csv) | 124 | 4096 | 16 个音频时钟 | 7 个完整非零 24 位样本 |

三份采集的逐位检查均通过：左右声道各 32 位时隙，声道切换后先延迟 1 位，再传输 24 位有符号 PCM，尾部 7 位填零。按标称 49.152 MHz 与每帧 1024 时钟计算，数字接口为 48 kHz。前两份的检查输出保存在 [verification.json](gao-48k-20260923/verification.json)，第三份保存在 [verification_reconnected.json](gao-48k-20260923/verification_reconnected.json)。

三份 CSV **不是同一次不间断运行**。第一次之后有一次 GAO 全零画面，Programmer 随即读到 User Code `0x0000A937`，不再是本次位流的 `0x000099EE`。`0xA937` 与[最初板卡扫描记录](板级验证-20260922.md)中的用户码相同，但**当时导致配置变化的事件尚未确定**，不能据此断言音频逻辑故障或长期保持可靠。重新下载同一位流后，读回 `0x000099EE`，GAO 恢复正常；在这次重新下载后的观察中，完成轮数曾从 173 增至 467，故障与欠载仍为 0，随后再次读回的 User Code 仍为 `0x000099EE`。

第三份采集发生在明确重新接入 12 V 电源及 DEBUG USB、开机之后。新一轮扫描读到 GW5AT-60B（ID `0x0001481B`）和初始 User Code `0x0000A937`；将**同一份** 48 kHz GAO 位流重新下载到 SRAM 后，独立读回 User Code `0x000099EE`、Status Code `0x70026020`。GAO 再次显示 PLL 锁定、64 声部工作、故障与欠载为 0；这次采集在完成轮数 124 时导出并通过检查。采集后再次执行只读 Read Device Codes，User Code 仍为 `0x000099EE`、Status Code 仍为 `0x70026020`。重新上电后 SRAM 配置不再保留，符合本次仅写 SRAM、未写 Flash 的操作方式；**不能用这一已知的断电事件解释前述原因不明的配置变化**。第三次也没有写入 Flash 或测试外接 DAC。

第一次 CSV 沿用 GAO 默认的 `1 us` 导出时间轴，与实际时钟不符。第二、三次设置为 `20345 ps`，是标称 49.152 MHz 周期四舍五入后的近似值。三份文件的时间列均由导出设置产生，**不是外部仪器的独立频率测量**；检查脚本按连续行号表示音频时钟周期。

## 外置 DAC 的预备引脚核对

对照 [Sipeed Tang Mega 60K 官方硬件资料](https://wiki.sipeed.com/hardware/zh/tang/tang-mega-60k/mega-60k.html)所链接的 NEO Dock 31004 Rev 1.4 原理图第 7、19 页，以及官方全引脚约束，PMOD1 的 J8 接口有三个可作为 3.3 V 数字输出的候选脚：

| 拟接 DAC 信号 | J8 脚号 | 底板网络 | FPGA 球号 | 复用关系 |
| --- | ---: | --- | --- | --- |
| BCK | 11 | PMOD1_IO0 | Y21 | DVP 摄像头 VSYNC |
| LRCK | 9 | PMOD1_IO2 | AB21 | DVP 摄像头 HSYNC |
| DIN | 7 | PMOD1_IO4 | AA20 | DVP 摄像头 D7 |

J8 的 3、4 脚为 GND；1、2 脚为板载 3.3 V。以上是**待实物核对的候选接线**，并未加入本次 CST 或位流。PMOD1 与 DVP、40P 扩展信号复用，接 DAC 时不能同时让摄像头或其他模块驱动这些线。连接前须按实物丝印确认 J8 的 1 号脚方向，并核对到货 DAC 模块的供电要求；不能因为信号是 3.3 V 就推断模块一定可由 3.3 V 供电。不要改接 FPC10P：原理图明确其 IO 在 1.5 V 的 BANK9。

从项目根目录复核：

```powershell
python scripts/check-gao-capture.py --audio-clock-hz 49152000 docs/hardware/gao-48k-20260923/board_audio_48k_core0.csv docs/hardware/gao-48k-20260923/board_audio_48k_later_core0.csv docs/hardware/gao-48k-20260923/board_audio_48k_reconnected_core0.csv
```

本次只验证片内时钟比值、64 声部持续运行与数字 I2S 格式。PCM5102A 尚未到货，候选引脚的实物方向、DAC 电平与供电、模拟输出及绝对采样率均未在板外实测。下一步是检查 SRAM 配置偶发变化的复现条件，并在 DAC 到货后核对模块、完成物理引脚约束、接线及输出测试。
