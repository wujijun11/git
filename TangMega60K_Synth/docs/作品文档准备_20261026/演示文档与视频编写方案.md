# 演示文档与视频编写方案

[返回源码阅读入口](README.md)

本文是写作和拍摄方案，还不是宣称整机已验收的最终作品报告。没有收到官方提交模板、页数、视频时长和源码格式限制；以下结构可先准备，收到官方规范后再调整。

## 1. 用一条主线贯穿，而不是逐个展示文件夹

建议主线：**人的演奏动作→FPGA实时生成声音→多维控制改变声音→灯和屏幕帮助演奏→通过测量证明实时性与复音规模。**

作品名称沿用工程名“弦光”；一句话介绍可写成：

> 基于Tang Mega 60K的纯硬件实时电子乐器，采用25键电容交互与滑条控制，在FPGA中完成64逻辑声部、多音色及音效运算，并提供曲谱回放、灯光学习和蓝牙联动。

“64逻辑声部”是设计目标/代码能力。最终摘要中是否写“现场64音已验证”、延迟具体数值、OLED与灯板效果，要等当前提交版本完成相应实测后决定。

建议拆成四份材料，而不是一个文档同时承担全部职责：

| 材料 | 读者想知道什么 | 应放哪些内容 |
|---|---|---|
| 作品技术报告 | 怎么做、为什么这样做、证据在哪里 | 架构、算法、接口、定点、时序资源、验证、限制 |
| 演示PPT/视频脚本 | 现场能看到什么、亮点是什么 | 实物、操作、声音、灯屏和关键测量 |
| 快速使用说明 | 拿到实物怎样安全启动、演奏和复现 | 供电接线、版本下载、滑条菜单、蓝牙、故障排查 |
| 源码包README | 从哪个入口构建、第三方来自哪里 | 顶层、目录、工具版本、命令、参数、授权、源码/位流哈希 |

## 2. 技术报告按这个顺序写

### 第1章：需求与方案

先用一页表把赛题要求对应到本项目：至少4复音、拓展32复音、至少两种交互维度、至少三维表情、多音色、音效、延迟和可视化。不要自行编造分值。

解释选择64逻辑声部、25个实体键、48kHz/24位I2S的原因：实体键数量不是复音上限，尾音、录音和曲谱可以共用更大的声部池。

### 第2章：整机硬件与结构

画实际连线图和分层装配图，明确Tang Mega、三片MPR121、无源键盘/滑条、C3、PCM5102、功放、喇叭、OLED、25灯与电平转换的职责。把电源、地、信号分别画清；引脚以提交版CST和实物核对表为准，不凭照片猜。

箱体/PCB若尚未制造或装配，标为设计图；实物照片与CAD渲染图分开标注。触摸电极板不含MPR121，DAC与功放也不是同一模块。

### 第3章：FPGA架构与时序分工

以`board_contest_full_top → instrument_full_system`为入口，画采集、控制、音频、录放、显示五块。说明50MHz参考、49.152MHz音频时钟、视频时钟与复位释放。解释1024拍/采样帧的预算以及分时流水方式。

重点讲`event → cmd → sample`和`done`回收，用一张NoteOn、NoteOff、Release、Done时序图说明握手。另画参数在`engine_sample_begin`提交/读取的时序，说明一帧内64声部使用同一份表情快照。

### 第4章：声音如何实时合成

先用DDS公式解释音高：`频率 = 频率控制字 × 采样率 / 2^32`。再讲查表、ADSR、力度、混音、定点扩位和饱和。用一个16位有符号样本、64路求和至少22位的简单例子引出实际中间位宽；不能只写“用了大位宽所以不会削波”。

八成分钢琴单独一节：四音区参数、8个分量的频率/幅度随时间变化、I/Q转幅相的资源取舍、两条通道分时计算。FM作为可切换音色另述。说明参考钢琴单音只用于离线提取数学参数，FPGA保存参数和周期表，不触发原录音。

给出采样帧计算框图、音色包络/频谱对比、ROM规模及实际资源报告。音色好听是主观结果，可提供同音高同力度同音量的对比；不要把离线模型WAV写成真实HDL或DAC实测。

### 第5章：交互、表情与菜单

从MPR121快照讲到事件化；说明实体选音与滑条音量可独立控制。弯音、颤音等逻辑能力和实际传感器维度分开计数，固定力度100不能写成压力检测。

画菜单状态图：默认音量→长按左端总菜单→四个子页；子页左长按回总菜单、右长按回音量，只有空闲总菜单5秒自动回归。OLED画面标明四区与滑条位置对应。

### 第6章：音效、曲谱、录放与学习

音效说明干声/延迟/混响/合唱、历史RAM及稳定反馈；录放说明“保存事件而非PCM”。将三种播放分清：上传RAM后脱机播放、电脑持续BLE传事件、25键学习/指引。

展示1024事件限制、直接MIDI音高模式、当前音色的使用规则。学习展示“目标和弦没按齐就等，按错不前进，松手后进入下一组”，不声称已有节奏评分。

### 第7章：上位机与通信

用手机/电脑→BLE→C3→UART→FPGA一张图解释职责。软件层按界面、协议、调度、曲库、存储、原生驱动分模块说明。搜索/推荐失败会使用缓存并标注；曲谱来源与许可随导入保留。

写明快速演奏如何避免多余等待、ACK与队列如何限制积压，以及失联怎样释放远程挂音。BLE往返时间单独展示，不能代替实体触摸通路延迟。

### 第8章：验证方法与结果

按“模块测试→整机接口仿真→布局布线STA→实物测量”逐层给证据。每项表格有版本、条件、起点终点、工具、结果、原始文件。

重点放三项：64音独立正弦谱峰/削波、实体触摸到音频的延迟、完整工程资源/时序。当前已有的是指定场景的数字接口仿真；实测空位留空，不能估算后填成实测值。

### 第9章：问题、取舍与改进

可以写已经有证据的设计取舍：幅相参数降低实时计算开销、共享音效存储、控制路径寄存边界、显示采用观察通路不阻塞音频。旧失败候选只需选一例说明“为何没采用”，正文不必复制全部开发日记。

剩余问题直写：BSRAM和时钟布线资源较紧、真实总延迟待测、当前音量页未加入旧客户端模式编码、长期稳定性和灯序/OLED需实物验收。未解决的现场噼啪/掉音现象不能仅凭仿真归因成功放或代码。

### 第10章：复现与附录

放版本/哈希、构建测试命令、接口字段、接线表、文件用途索引、第三方授权和分工。分工按实际完成内容填写；此前“队长/A/B”的称呼可改成具体职责，不能把第三方BLE库或PLL算作原创。

## 3. 演示视频可以先按6～8分钟排练

以下时长只是建议，不是赛事规定。若官方限制更短，优先保留实体演奏、纯HDL证据、64复音和延迟测量。

| 建议段落 | 展示动作 | 应让观众明白 | 拍摄/证据要点 |
|---|---|---|---|
| 0:00～0:30 | 实物全景、演奏一小段 | 这是能操作的完整乐器 | 显示板卡、键盘和喇叭；注明本次版本 |
| 0:30～1:30 | 单音/和弦、持续按键同时滑动音量 | 两个动作维度独立，过渡连续 | 手和屏幕/滑条同框；不要用电脑演示音替代 |
| 1:30～2:30 | 同音高切钢琴/风琴/FM，切音效 | 多音色和硬件音效确实生效 | 固定力度与音量、先干声再效果，避免大声误判更好听 |
| 2:30～3:30 | 录一小段、停止、断开客户端后板上回放 | 存事件、FPGA实时重合成、能脱机 | 版本与RAM保留条件讲清；不要断FPGA电源 |
| 3:30～4:30 | 5×5灯和编号；按错/未按齐/按齐学习和弦 | 灯是演奏指引，学习会等人 | 先完成实物灯序校准，键号贴纸清晰 |
| 4:30～5:15 | 软件搜索/本地MIDI、上传、直接音高播放 | 曲谱扩展与25键限制的处理 | 备用本地合法MIDI，避免现场网络失败卡住 |
| 5:15～6:15 | 64音自检与目标频谱 | 独立频率、真实48kHz输出、非录音播放 | 用正弦/中性表情/关闭延迟；代码与采集方式对应同一版本 |
| 6:15～7:15 | 示波器延迟/STA资源表/HDMI观察 | 实时指标有清楚的测量边界 | 屏录保留时间基准和起止定义；没有实测就改为仿真说明 |
| 7:15～结尾 | 架构、创新和限制各一句 | 评审能复述作品核心 | 不用“所有要求均达标”等笼统结论 |

64音自检的可综合源已存在，但它目前是独立诊断入口，不应在视频中假装标准主工程已有某个“一键64音测试”菜单。正式演示前需选择并固定经过验证的诊断入口/切换流程，以及对应的CST和位流。

## 4. 现在就能准备的图表和素材

1. 一张整机数据流图、一张真实供电/信号接线图、一张模块层次图。
2. 单音NoteOn到Done时序、表情帧提交时序、1024拍预算图。
3. 钢琴8成分框图、ADSR曲线、定点位宽表、干声/音效框图。
4. 滑条菜单状态图和OLED四区画面；仿真渲染图标“仿真预览”。
5. 曲谱上传/实时播放/学习三种路径对照，灯号1～25对应图。
6. 64个理论频率、仿真FFT与以后DAC实测FFT的独立图表。
7. 资源/时序表、延迟分段表、验证结果矩阵。
8. 原创与第三方清单、功能分工、已知问题和复现入口。

先用这些材料搭报告骨架，再补真实照片、录屏和测量；不要先写满“已达标”，再去找证据。

## 5. 写作时统一这些术语

- 64声部是逻辑发声位置；25键是实体选音范围；立体声是最后左右两个输出。
- 1024条是曲谱事件容量，不是1024首曲子；按下和松开通常各占一条。
- 参考样本用于离线拟合；HDL仿真WAV来自RTL输出；DAC实测音来自真实模拟输出，三者分别标注。
- HDMI“64频点Goertzel显示”不写成“完整实时FFT”；64音评分验证使用独立频谱分析。
- 时序余量单位ns，反映电路内部路径是否满足时钟；演奏延迟单位ms，反映动作到声音多久，两者不是同一个指标。
- 软件提供模拟器/本地试听是开发便利；纯硬件发声证明必须使用真实FPGA输出通路。
