# 开关式延音、菜单与蓝牙控制实现说明

日期：2026-10-30。分支：`codex/sustain-20261030`。
基线：Chord F571，提交`df6e8f6f8fcc60a31d0ff549eab37640f67aa4f7`。
状态：独立本地测试版；最终结果由`docs/reports/sustain-20261030/analysis.json`核对。
新增功能尚未实际下载/上板验收，不替换用户选定的F571。2026-10-30按用户要求发布独立测试分支；
最初冻结交付包内“未推送”描述保留为打包时历史状态，当前发布范围见releases/sustain-20261030/README.md。

## 1. 做了什么

增加一个默认关闭的延音开关，板上菜单、Windows和Android都可设置。
延音开启后，松开琴键不立即进入释放阶段；钢琴继续使用原有八成分参数合成和自然衰减。
关闭延音时，已经松开的声部进入原有约100ms全幅释放斜率，仍按住的声部继续发声。

延音不是40ms回声，也不额外增加混响。风琴和正弦使用原来的持续音色，因此开启延音后会保持声音，
直到关闭延音或全部停止。钢琴本身仍会逐渐变轻；这不是完整的琴弦/制音器物理模型。

保持49.152MHz音频时钟、48kHz、64声部、左右24位有符号PCM、标准Philips I2S每声道32位槽。
没有新增PLL、引脚、PCM录音播放、DDR或外接踏板硬件；C3固件不变。
没有合入已撤回的计数器缩位版，也没有合入另一分支的OLED波形美化实验。

## 2. 操作方法

长按滑条左端进入总菜单，选择“声音”。声音页四区改为：

| 第一区 | 第二区 | 第三区 | 第四区 |
| --- | --- | --- | --- |
| 音色 | 音区 | 音效 | 延音 |

延音设置页：

| 第一区 | 第二区 | 第三区 | 第四区 |
| --- | --- | --- | --- |
| 关闭延音 | 开启延音 | 返回声音页 | 返回主菜单 |

OLED显示实际开关状态。选完关闭/开启后显示波形，再触摸回音量；菜单闲置10秒、左长按进入总菜单、
右长按回音量等规则继续沿用。原声音页第四区“返回”由延音入口替代，返回路径放在延音设置页。
其他音色、音区、音效、表情、录放、曲谱操作不改变。

Windows 1.5.2-sustain-test和Android 1.9-sustain-test增加“延音”复选框。
连接时先读取板上能力：新测试版可控制，原F571保持正常连接但禁用新开关。
开关显示依据实际回读，不凭点击动作直接认定已生效。
“保留x/64”表示已经松键但尚被延音保留的声部，不包含仍按住的键或已进入RELEASE的尾音。

简单试听：先关闭延音，短按一个钢琴键并松手；再开启延音，重复操作并接着弹其他键。
最后关闭延音，检查旧尾音收住，而仍按住的键继续发声。

## 3. 为什么放在命令边界

```text
实体键 / 曲谱 / 蓝牙音符
        ↓ 原V2事件队列
原voice_allocator_v2（来源、音高、64槽所有权）
        ↓ 原cmd_*格式
sustain_command_gate（新增，逐声部暂缓OFF）
        ↓ 原cmd_*格式
原voice_engine（DDS、ADSR、八成分钢琴、混音与峰值保护）
        ↓ 原音效、I2S
PCM5102 / 功放 / 喇叭
```

原分配器、`captain_control_top_v2`、`expression_controls_v2`及音频运算RTL保持不变。
不增加音源source字段，不绕过声部分配器，不改公共V2事件/命令/完成/样本接口。
内部包装层增加开关和状态观察线，不增加板外引脚。

正常ON/OFF只有在音源实际接受命令时才向分配器确认。延音期间OFF由延音模块确认并记入64位位图；
原分配器把该键记为已松开，但槽位仍active，直到关闭延音、音源完成释放并通过done回收。
因此不会把仍发声的槽当成空闲槽重用，也不会误把尾音回收成另一个人的音。

## 4. 核心状态与边界处理

| 控制状态 | 职责 |
| --- | --- |
| IDLE | 决定普通转发、保留OFF或补发释放 |
| FORWARD | 寄存冻结普通命令，等待音源接受后同时确认原分配器 |
| DEFER | 确认已松开的键，将对应声部标为延音保留 |
| SCAN | 逐槽寻找待释放声部，避免新增64路优先编码长路径 |
| RELEASE | 冻结补发OFF，在音源接受后清除对应位和计数 |

- 输出valid一旦呈现，反压期间valid和所有负载保持稳定。
- 极快重新开启延音时，尚未呈现OFF的声音可被重新保留；已经呈现的OFF继续完成，不撤回事务。
- 新ON清除同一槽的旧待释放标记，避免以后误关新音；正常分配器不会提前重用未done的槽。
- 全部停止、复位清除开关、位图和音源状态；原断连看门狗进入释放时也关闭开关。
- 普通曲谱停止继续提交原有松键事件，开启延音时仍服从踏板；“全部停止”会明确清除延音。
- 常规命令增加一个注册准备拍，49.152MHz下约20.35ns；采样边界附近可能改变命令进入哪一帧。
  不把这个数字当作传感器到喇叭总延迟，也不承诺任意持续反压下的固定延迟。

## 5. 重复同音与64声部

开启延音后，同一键松开再弹，旧声部仍在延音，新按下可由原分配器取得另一个空槽。
这会产生叠加的声音，符合本版“旧音不断、新音重新起音”的设计。
仍按住时的重复触发继续使用原分配器和音源的既有重触发规则。

总声部上限仍是64，不增加偷音策略。64槽占满时，新音按原满载规则拒绝；
关闭延音后需要等待释放和done回收，不能把已发出OFF等同于立即空槽。
钢琴已衰减到很轻的延音仍可能占槽；本次不新增静音检测回收，以免改变原音色尾部。
原稳定和弦标度与双声道峰值保护保持不变。

## 6. 蓝牙兼容扩展

C3仍透明转发16字节协议帧并校验既有CRC；不用重新刷C3。
不改变旧操作含义，不占用旧0x83的保留字段。

| 请求 | 新测试版行为 |
| --- | --- |
| CONFIG 0x03，payload[0]=2，payload[1]=0/1，其余0 | 设置延音关闭/开启，正常ACK |
| READBACK 0x08，payload[0]=5，其余0 | ACK后返回0x86状态帧 |
| 新设置值大于1、查询含非零索引或保留字段 | NACK status=1，不改变开关 |

0x86的10字节payload：

| 字节 | 内容 |
| --- | --- |
| 0 | 扩展格式版本1 |
| 1 | 实际延音开关0/1 |
| 2 | 已松键且被保留的声部数0..64 |
| 3 | 声部容量64 |
| 4..9 | 保留，必须为0 |

同seq重试返回原事务ACK/快照，不重复提交开关。客户端只在能力探测通过后发送CONFIG target2；
旧F571对selector5返回不支持时，旧功能继续使用，新开关显示禁用。
0x86曾在未采用的诊断实验中使用，不能把那份实验客户端/位流与本包混用；本包严格核对格式与容量字段。

闲置时按既有心跳节奏附带查询状态，避开已经排队的演奏、按住的虚拟键和批量任务。
快速按下/松开仍完整发送，继续保留Windows 1.5.1原生后台调度及连接租约处理。
本轮没有移植Windows后台线程到手机，也没有新增MIDI CC64导入。
录制仍只记录原来的音符事件，不记录开关切换；回放采用当时的延音状态。

## 8. 验证口径

本版交付脚本要求34个HDL测试入口通过：新增10项及原有24项。
新增覆盖4/64声部控制、原分配器满载/回收/同音重弹、ready/valid反压、开关快速切换、
协议非法参数/相同seq重试/快照冻结、真实菜单及UART、完整64声部同时延音和释放。

完整逻辑整合使用原MPR数字快照边界注入和真实UART帧；保留原音源和I2S，检查持续PCM、
延音期间无OFF、关闭后只释放已松键声部、PANIC与看门狗清除。
该逻辑测试使用加速测试时基/UART，不据此报告板卡真实频率或声学毫秒延迟；
另有原49.152MHz板级PLL/I2S及生产OLED总线时序回归。

| 独立分析 | 结果 |
| --- | --- |
| OLED实际渲染字节与可读文字/字体参考 | 三整屏、3072字节一致 |
| 延音关闭，4声部钢琴，帧内同样命令 | 8168帧左右PCM逐位一致 |
| 延音关闭，64声部正弦，帧内同样命令 | 8288帧左右PCM逐位一致 |
| 原Chord钢琴、正弦PCM CSV | 与F571历史SHA256一致，由封存脚本再次检查 |
| 状态变化到首个非零I2S的数字延迟 | 四个场景分别为1.414607、0.939365、0.365465、1.908689ms，与F571相同 |

中性对照将两边包络同样加速为0/0/1ms，覆盖帧内命令、满载与输出反压；
不推广为任意采样边界到达时间的逐周期等价。完整整合另外使用生产100ms释放参数。

触摸延迟CSV的绝对时间戳并非逐字节相同：新增命令准备拍使后续场景起点也有移动。
按每个场景的状态变更时刻归一化后，上述四种数字总延迟相同，首条命令确认较基线多20～21ns。
不能把原始文件哈希不同误报成音频算法改变，也不能把这些数字当作手指到喇叭的实测延迟。

客户端最终执行21条检查命令，其中1条生成独立MIDI参考，其他包括协议、控制器、
快速按键队列、原生租约、实时调度、手机流程、真实本地页面、52项Python检查、
2000组Python/JS帧参考、Android链路策略、实际MainActivity回调及三类异步操作。
真实页面的设备为协议模拟器，Android宿主为JVM替身，均不是实际射频测试。

Windows打包资源逐文件核对并运行离线依赖自检；APK执行assembleDebug、lintDebug及v1/v2签名检查。
Android lint错误/警告为0；签名工具关于AGP元数据未受JAR签名保护的提示、JVM替身的Unsafe警告均保留日志。

## 12. 遇到的问题与解决

1. 首次编译发现新状态寄存器引用了尚未声明的内部线；把控制always块放在声明之后，未改时钟/复位协议。
2. 测试台的回传变量声明顺序同样被ModelSim拒绝，移动声明后重跑；这两轮失败日志不计通过。
3. 钢琴/正弦等价用例复用了同一CSV文件名，后跑覆盖前跑。按音色分别命名，重新运行专项和回归并保留独立记录。
4. 手机重连测试原先硬编码三次状态读回，新增能力探测后应为四次；改为同时断言selector5恰好一次，继续检查握手期间没有音符插队。
5. 旧Android宿主测试不是unittest入口且遗漏当前生产依赖/API。使用原CLI参数、编译全部实际Java依赖，
   补齐链路优先级、特征属性与文件选择类型的系统替身；没有因此改App生产逻辑。
6. MIDI检查缺独立生成的fixture，先用已有mido参考生成器生成再运行，未把缺输入当成业务失败或通过。
7. 新准备拍改变延迟测试的绝对时间戳；实际逐场景对齐状态变化起点后，四个I2S总延迟一致。
   因此保留原始不同的CSV和差异明细，不再把该文件写成SHA256一致。

各轮失败/修复及最终结果保留；最终封存要求源码指纹、像素、样本、安装包和位流报告一致。
