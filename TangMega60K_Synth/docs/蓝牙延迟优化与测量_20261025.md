# 蓝牙延迟优化与测量

## 当前真实结果

用户将 `ContestFull_ModeSync1024.fs` 下载并确认Finished后，对现有C3执行24次状态查询。只发送READBACK0，没有NOTE、CONFIG或PANIC；未改音色、键位或音量，也未更新C3固件。

| 24次查询的测量 | 现有连接中位数 | 现有连接P95 | Windows性能偏好试跑中位数 | 试跑P95 |
| --- | --- | --- | --- | --- |
| GATT写操作完成 | 59.2 ms | 98.5 ms | 26.6 ms | 33.9 ms |
| FPGA ACK返回 | 59.0 ms | 97.8 ms | 41.0 ms | 50.9 ms |
| 完整状态返回 | 66.6 ms | 98.2 ms | 58.4 ms | 74.0 ms |

后一个试跑申请Windows公开的吞吐优化预设，实际读取到15ms连接间隔、从机延迟0。**两次试跑是不同连接、并非严格控制无线条件的A/B实验**，不能将全部差值归于该申请；更不能把它写成“优化后发声延迟58ms”。GATT写和ACK可能重叠，不能简单相加。

状态查询有ACK和遥测两帧回复，普通音符命令通常只有一帧ACK；这些数据不是按键到DAC或喇叭的声学延迟。最后应使用GPIO触发与I²S/模拟输出同步测量。初次未确认FPGA程序时曾完全无返回，已保留失败记录，未把3秒超时当成正常延迟。

证据：`verification/ble-latency/live-fpga-ready.json`、`live-windows-fast.json`；只读失败路径在 `live-diagnostic.json`。原C3错误计数均为0，24次有效状态完整返回。诊断特征每100ms更新，不能要求查询结束瞬间的流量计数与最后一帧完全同步。

## 改进了哪些等待

1. C3成功通知不再固定隔15ms。主循环仍让出1ms；失败重试保留15ms退避、三次失败关闭、会话隔离、错误计数和队列保护。
2. C3在新连接回调中申请7.5–15ms间隔、从机延迟0。最终值由主机和设备协商，申请值不能冒充实际值。
3. Windows连接期间通过公开WinRT API申请ThroughputOptimized，断开后释放请求和本模块持有的设备引用；旧Windows/不支持时回退，不改系统驱动、注册表或全局电源设置。
4. Android申请CONNECTION_PRIORITY_HIGH；拒绝时继续工作。依据设备实际声明的属性，电脑和手机可以省去ATT写响应；旧C3只有WRITE属性时保持原写法。
5. 每条命令仍等FPGA应用ACK，保留相同序号重试、CRC与错误处理。没有不受控流水发送；正常短音的按下/松开完整保留，不靠漏音减小积压。
6. 演奏命令正在传输/排队时，后台状态查询不继续加入队列；空闲恢复。任何有效命令都能刷新FPGA现有通信看门狗，因此正常忙碌期间无需额外查询插队；长按不动时仍保留空闲心跳。

16字节UART帧在115200、8N1下线路时间约1.39ms，命令加一帧ACK约2.78ms，不包含各层调度。此次不改UART波特率，不改公共音源V2接口，不改音色或DSP算法。

## 如何使用

新版客户端位于 `delivery-ble-latency`。Windows程序必须保留整个目录；手机为Android1.5。原模式同步、搜索、MIDI和1024事件功能保留。FPGA位流与用户刚下载的文件相同，没有要求为了客户端优化再构建或重刷FPGA。

旧C3固件仍有15ms固定等待，并且只有带响应WRITE属性。更新电脑客户端可以先使用Windows偏好申请和后台避让，但C3侧的全部优化需要把新C3固件写入后才能生效。C3固件是ESP32二进制，不是FPGA的`.fs`；不要在Gowin Programmer里选择C3二进制。

本轮仅编译/整理C3固件，没有上传。待更新C3后，用相同脚本、相同位置、相同蓝牙适配器、相同样本数重测；Windows/手机不能同时占用该桥。仍未实测优化后的C3射频、真实快歌听感或按键到DAC延迟，不能宣称整机达到5ms。

## 复现命令

```powershell
# 需先断开其他客户端；只读查询，不发声。
./tmp/desktop-python/Scripts/python.exe scripts/probe-ble-latency.py --count 24 --output verification/ble-latency/baseline.json
./tmp/desktop-python/Scripts/python.exe scripts/probe-ble-latency.py --windows-fast --count 24 --output verification/ble-latency/windows-fast.json

# 普通软件测试，不连接硬件。
node desktop/tests/test_queue.js
node desktop/tests/test_controller.js
node desktop/tests/test_mode_sync.js
./tmp/desktop-python/Scripts/python.exe desktop/tests/test_ble_link.py
./tmp/desktop-python/Scripts/python.exe desktop/tests/test_native_write.py
./tmp/desktop-python/Scripts/python.exe desktop/tests/test_ble_probe.py
./tmp/desktop-python/Scripts/python.exe mobile/tests/test_ble_policy.py
```

编译工具由 `scripts/bootstrap-ble-tools.py` 安装到英文临时目录：Arduino CLI1.5.1、ESP32核心3.3.5，使用官方来源与校验值。Windows系统代理仅写到本任务工具配置，不改变系统设置。`build-ble-bridge.ps1 -ToolRoot <工具目录>` 只编译、不上传。完整固件编译与校验以交付 `c3/build-manifest.json` 为准。

实际测试还包括11组队列/生命周期测试（含100条快速演奏事件不丢弃及后台避让）、3组Windows租约测试、2组原生写入、2组只读探针、Android策略、C++通知策略、原曲库和手机模式/上传回归。APK组装、lint、签名和Windows打包自检有独立日志。

## 评分与演奏边界

实体触摸键直接进入FPGA，不需要经过蓝牙。蓝牙模拟键和上传曲谱是另一条控制路径。现有协议逐命令等ACK，持续输入超过吞吐仍会排队；继续提高和弦/快弹上限可能需要有界批处理、时间戳及更完整的重试窗口设计，不能简单同时乱发或静默丢音。本轮不擅自改变既有16字节协议。

官方依据：[Windows连接偏好](https://learn.microsoft.com/en-us/uwp/api/windows.devices.bluetooth.bluetoothledevice.requestpreferredconnectionparameters)、[连接间隔单位](https://learn.microsoft.com/en-us/uwp/api/windows.devices.bluetooth.bluetoothleconnectionparameters.connectioninterval)、[Android优先级申请](https://developer.android.com/reference/android/bluetooth/BluetoothGatt#requestConnectionPriority(int))、[Bleak写入语义](https://bleak.readthedocs.io/en/latest/api/client.html#bleak.BleakClient.write_gatt_char)。
