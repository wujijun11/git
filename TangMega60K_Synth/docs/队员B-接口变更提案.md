## 提案一：key_id / channel

### 问题：两个琴键弹同一个音，会坏成什么样

这不是"听起来有点怪"，是一条可以逐步跟出来的具体故障。
假设两个独立琴键 A、B 都映射到音符 60，依次按下：

| 步骤 | 分配器内部（行号见 `rtl/voice_allocator.v`） | 结果 |
|---|---|---|
| A 按下 | SCAN 无 match，`free_id=0`；SEND 置 `held_mask[0]=1`、`note_mem[0]=60` | 声部 0 发声 |
| B 按下 | 第 107 行 `held_mask[0] && note_mem[0]==60` 命中 → `found_match=1`，`cmd_voice=0` | **B 复用了声部 0，A 的音被重触发，两个键只有一个声部** |
| A 松开 | 同一条匹配再次命中 → `cmd_on=0` → 释放声部 0 | **B 还按着，音却停了** |
| B 松开 | `held_mask[0]` 已是 0，匹配不中；`active_mask[0]` 仍为 1（尾音），无空位 → `ignored_pulse` | **B 的松开被静默忽略** |

四步里错了三处。根因是一句话：**第 107 行的匹配条件是"音符相等"，
而"释放哪个声部"用的也是这同一条匹配** —— 分配器无法区分"哪个键"，
因为接口里根本没有这个信息。

### 关键结论：只加宽事件**修不好**这个问题

这是本提案最需要队长注意的一点。若只把事件从 17 位加宽、塞进一个 `key_id`，
`event_fifo` 确实能把 key_id 原样送达，但分配器**拿到就扔** ——
它锁存 `pending_note`，不锁存 `pending_key`；匹配时比的是 `note_mem`，不是 `key_mem`。
结果是：**接口变了、兼容性破了、问题一点没好。**

必须同时改三处：

| # | 文件 | 改动 |
|---|---|---|
| 1 | `rtl/event_fifo.v` | `EV_WIDTH` 17 → 17+KEY_WIDTH，位映射与四条 `assign` 同步 |
| 2 | `rtl/interaction_top.v` | 输入端口加 `in_key`，输出端口加 `event_key` |
| 3 | `rtl/voice_allocator.v` | **新增 per-voice `key_mem` 数组**；`pending_key` 锁存（约第 93 行处）；匹配条件（第 107 行）改为 `held_mask[scan_id] && note_mem[scan_id]==pending_note && key_mem[scan_id]==pending_key`；SEND 里写 `key_mem[cmd_voice]`（约第 134 行处）；复位里随 `note_mem` 一起清（约第 74 行处） |

第 3 项由队长改（`voice_allocator.v` 是队长的文件），第 1、2 项由我改。

### 代价（估算，非实测）

| 项 | 计算 | 寄存器 |
|---|---|---|
| FIFO 加宽 | 32 深 × 6 位 | +192 |
| `key_mem` | 64 声部 × 6 位 | **+384** |
| 合计 | | **+576（估算）** |

**代价的大头不是 FIFO，是 `key_mem`。** 它是 per-voice 而不是 per-event 的，
64 个声部每个都要记住自己属于哪个键。所以"加宽事件很便宜"这个直觉是错的。

KEY_WIDTH 取 6 与 `VOICE_COUNT` 对齐；若琴键数量已知且少于 64（例如两个八度 25 键），
取 5 位可省 64 个寄存器。

### 一个更便宜但语义有损的替代方案

若认为 +576 寄存器不可接受：不加 `key_mem`，改为**把"同一个音符在按住状态下被再次按下"
当作无操作**（不回退到复用，也不新增声部），释放时也只有最后一个松开才生效。
代价是**两个键弹同一个音时只出一个声部，且松开顺序无法区分** —— 问题从"错得很隐蔽"
变成"限制写进文档"。**这个方案的好处是 `voice_allocator` 几乎不用改存储**。
两种方案请队长选。我的建议是：**若传感器支持多点且用户可能弹同音，做完整 key_id；
否则明确写成限制，省下 576 个寄存器。**

## 提案二：持续表情（压力）与全局滑音

### 为什么不能用现在的事件接口

当前 17 位事件里**没有、也不该有**表达压力的字段。这看似是缺陷，实际是优点：
它从结构上强制了文档第 32 行的规定 —— 你**没法**用重复 note-on 去模拟持续压力，
因为接口里除了 note-on / note-off 之外没有别的事件可发。
这是值得在文档里明确主张的设计优点，而不是待补的缺口。

### 压力的本质：它是**状态**，不是**事件**

这是本提案的核心论点，也是接口怎么定的唯一依据：

| | 音符事件 | 压力 |
|---|---|---|
| 性质 | 离散、一次性 | 连续、可持续变化 |
| 每次更新都重要吗 | 是，一条都不能少 | **否，只有最新的值重要** |
| 合适的载体 | 队列（FIFO） | **寄存器 + 覆盖式握手** |

**把压力塞进 `event_fifo` 是错的**，原因不是"要多加字段"，而是排队会**延迟**它：
一次 16 音和弦按下会在队列里排 16 条事件，按每条 ~66 周期算，排在后面的压力更新
要等一千多个周期才被取出 —— 而那时它已经过时了，取出来的还是**旧值**。
连续量排队，等于用最长的延迟去送最短的时效。

### 建议的接口形状（草案，待讨论）

单独一组端口，不经过 FIFO：

```text
expr_valid / expr_ready          // 覆盖式握手，不接受时生产者保持，落败的旧值直接丢弃
expr_target[5:0]                 // 目标声部编号，或保留值表示"按音符解析"
expr_param[1:0]                  // 参数编号：0=压力 1=音色亮度 2=弯音 …
expr_value[6:0]                  // 参数值
```

两个语义要点：

1. **`expr_ready` 可以一直为高。** 与事件不同，压力更新被覆盖是**正确行为**，
   不是丢数据。所以这一路几乎不会被反压，也不需要排队。
2. **目标是"声部"还是"音符"要先定。** 若定成音符，分配器必须自己做 note→voice 解析；
   若定成声部，则是由控制侧跟踪分配结果。**建议按音符**，因为控制侧不应该知道分配细节，
   而且同音多键一旦做了 key_id，控制侧手里的"音符"也不足以唯一定位声部（要带 key_id）。
   但按音符解析需要分配器提供一次查询，代价要队长评估。

### 跨到队员A 的那一段

压力最终要进合成引擎，而引擎目前的命令接口是 `cmd_*`（note/velocity/timbre/voice）。
所以这个提案**必然牵动队员A**：要么扩展 `cmd_*` 增加参数类命令，
要么给引擎开一路独立的参数端口。**这是三人接口，不是B一个人的事**，需要一起定。

另外，全局滑音比压力更麻烦一层：它是**全局**的（不属于任何声部），
而且连续改变音高，对时序比对音符事件敏感得多 —— 需要明确"这个值从哪一个采样点开始生效"。
**建议把全局滑音与 per-voice 压力分成两件事**，不要挤进同一组端口。

### 代价

无法像提案一那样给出寄存器估算，因为方案尚未成形（命令走 `cmd_*` 还是新端口、
按音符还是按声部，都会改变量级）。**这一项目前只有定性判断，没有数字。**

## 两项提案的共同点

- **都要改公共接口**，因此都要先确认再动手。
- **都不是只改 B 侧就能完成的**：提案一要改 `voice_allocator`，提案二还牵动队员A。
- 本轮的代码**与这两项完全无关**，不必等它们就能集成 —— 17 位事件接口是自洽可用的。
